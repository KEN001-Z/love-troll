# Supabase integration

VYBE is a multi-page static site built with Vite. It uses the existing Supabase project `vhkzyasknygybugugjyl` in `eu-west-1`.

## Local development and deployment

1. Install dependencies with `npm install`.
2. Copy `.env.example` to `.env.local` and set `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY`. The URL and publishable key are browser-visible values. Never use a service-role key or secret key here.
3. Run `npm run dev` during development and open the Vite URL it prints (normally `http://localhost:5173`). Do not use VS Code Live Server to open the source HTML directly: it does not resolve the Supabase package or inject the Vite environment variables. Run `npm run build` for a static deployment; the output is in `dist/`. Netlify builds use [netlify.toml](./netlify.toml) to run that command and publish `dist/`; do not publish the raw project root.
4. Configure the deployed origin and the `login.html`, `onboarding.html`, and `reset.html` paths in Supabase Authentication → URL Configuration. For local development, allow the Vite origins `http://localhost:5173/**` and `http://127.0.0.1:5173/**`. Configure the email templates/provider if email confirmation or password recovery messages need delivery.

Vite embeds `VITE_` variables in client assets at build time; configure `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` as Netlify build environment variables before deploying. These are browser-visible values; never put a service-role key or secret key there. `.env.local` is ignored by Git.

## Google sign-in

Google sign-in is available on both the login and signup pages. Before users can use it, create a **Web application** OAuth client in Google Cloud, add the local and deployed site origins as authorized JavaScript origins, and add the callback URL shown in Supabase Authentication → Providers → Google as an authorized redirect URI in Google Cloud. Then enable Google in that Supabase provider settings page and enter the Google client ID and client secret there. Keep the client secret in Supabase; it does not belong in `.env.local` or browser code. Also allow the deployed `login.html` and `onboarding.html` redirect URLs in Supabase Authentication → URL Configuration. Signup with Google still requires users to confirm they are 18 or older and accept the VYBE terms before redirecting to Google.

## Database

The connected project initially had no tables in `public`, no public RLS policies, and no migration history. Its base profile and onboarding migrations were already applied. The discovery and student-profile migrations are now applied to the connected VYBE project; run them in this order when setting up another environment:

- [supabase/migrations/20261011212040_track_vybe_onboarding_progress.sql](./supabase/migrations/20261011212040_track_vybe_onboarding_progress.sql) adds the current onboarding step so unfinished flows resume where users left off.
- [supabase/migrations/20261012103008_add_discovery_and_mutual_matches.sql](./supabase/migrations/20261012103008_add_discovery_and_mutual_matches.sql) adds authenticated discovery of completed profiles, private outgoing interests, and participant-only mutual matches. Interests are recorded by an authenticated-only RPC; a match row is created only after reciprocal interest.
- [supabase/migrations/20261012103403_add_student_profiles.sql](./supabase/migrations/20261012103403_add_student_profiles.sql) adds student profile details, private profile media, explicit matchmaking opt-in, and privacy-aware profile/discovery RPCs. - [supabase/migrations/20261012105101_remove_generated_profile_usernames.sql](./supabase/migrations/20261012105101_remove_generated_profile_usernames.sql) removes UUID-derived placeholder usernames. A username is now shown only after the student chooses one.
- [supabase/migrations/20261012105254_fix_generated_profile_usernames.sql](./supabase/migrations/20261012105254_fix_generated_profile_usernames.sql) corrects the cleanup migration's trigger ordering so existing UUID-derived usernames are actually cleared.
- [supabase/migrations/20261012180301_add_profile_gender.sql](./supabase/migrations/20261012180301_add_profile_gender.sql) adds the optional profile gender field.
- [supabase/migrations/20261012225912_create_posts_feed.sql](./supabase/migrations/20261012225912_create_posts_feed.sql) creates the text-post MVP, authenticated author-only edits/deletes, anonymous identity redaction, and the paginated public-feed RPC. This migration has been added to the repository but has **not** been applied to the live project.
- [supabase/migrations/20261012233000_create_community_chat.sql](./supabase/migrations/20261012233000_create_community_chat.sql) creates the six public Community rooms, authenticated message storage/RLS, cursor-paginated message history, private database Broadcast notifications, and authenticated Realtime Presence. This migration was applied to the live project through SQL Editor on 2026-10-12; verify migration history before using a future CLI push.
- [supabase/migrations/20261012234500_add_community_safety.sql](./supabase/migrations/20261012234500_add_community_safety.sql) adds anonymous-message redaction to the history RPC, server-enforced message sending with a 1,000-character limit, a five-message-per-minute limit, duplicate-send protection, private message reports, and a moderator-only hide foundation. Direct client inserts are revoked and the safety RPCs derive authorship/reporters from `auth.uid()`. This migration was applied to the live project through SQL Editor on 2026-10-12; verify migration history before using a future CLI push.
- [supabase/migrations/20261012241000_add_chat_identity_and_direct_messages.sql](./supabase/migrations/20261012241000_add_chat_identity_and_direct_messages.sql) extends public message responses with privacy-safe profile display names/avatar paths, adds single-message fetches for incremental realtime updates, and creates mutual-connection-only private conversations with member-scoped history, server-authored messages, unread/read state, pagination, rate limiting, private Broadcast topics, and private `post-media`/`direct-media` Storage buckets with path-based policies. It also extends the posts feed to support image and video posts. This migration is prepared locally and requires manual application to the live project before Messages or media uploads can work against Supabase.

The connected project's previously reported migration history records versions `20261011211437`, `20261011212040`, `20261012103008`, `20261012103403`, `20261012105101`, and `20261012105254`. The later profile-gender and posts migrations must be checked against the live migration history before applying. The Community-chat and Community-safety SQL were run successfully in the live project's SQL Editor, but manual SQL execution does not necessarily add a CLI migration-history row; reconcile that history before a future `supabase db push`. Do not rerun a migration already recorded as applied.

The student-profile migration adds profile photos, bio, education details, optional interests and tags, and visibility settings. Profile IDs are the authenticated Supabase Auth user UUIDs; the profile page uses `auth.getUser()` to identify the signed-in owner and fetches that owner’s row by the same UUID. Other profile IDs come from persisted profile rows and are checked by the database RPC against the current authenticated user and visibility rules. Names come from saved profile data or the owner’s Auth display-name metadata; usernames are never generated from IDs. The checked-in migration defines a private `profile-media` bucket for profile photos and covers, accessible to the owner, a campus-visible audience, or a mutual match. Post and DM media are defined by the later chat/media migration and require that migration to be applied. The live Storage dashboard could not be inspected in this session.

The posts migration permits authenticated, onboarded users to publish text posts. RLS binds inserts, edits, and deletes to `auth.uid()` and does not let clients change moderation status or timestamps. Direct table reads hide other users' anonymous rows; the authenticated feed RPC returns no author ID or name for anonymous posts and does not reveal another user's name or profile link when their profile is private. It only returns profile links for campus-visible profiles. The RPC returns only published posts, ordered by `(created_at, id)`, and supports `all` and `anonymous` keyset-paginated queries. Moderation can mark a post `removed` through trusted database administration; no moderation UI or reporting workflow is included. Polls, reactions, comments, competitions, image/video posts, and trending are not implemented.

To apply the new migrations safely:

1. Confirm the target is project `vhkzyasknygybugugjyl` (the project reference in this repository's `.mcp.json`) and check that version `20261012225912` is not already recorded/applied. The Community migration has already been run in the live SQL Editor.
2. Prefer the Supabase CLI migration workflow. From the repository root, link the CLI to this exact project with `supabase link`, verify the selected project, review all migrations that the CLI reports as pending, and run `supabase db push` only if every pending migration is intended for this project.
3. If you apply it through the Dashboard instead, open the SQL Editor from the dashboard for project `vhkzyasknygybugugjyl`, verify the project reference in the URL, and run the complete migration file once. SQL Editor execution does not itself record the migration version; reconcile migration history before any later CLI push to avoid applying it twice.

The CLI and a `supabase/config.toml` are not present in this workspace, and the Supabase MCP is unavailable in this session. The Community schema and safety additions were applied and verified through the authenticated Supabase SQL Editor for project `vhkzyasknygybugugjyl`. The later chat-identity/direct-message migration is local-only until it is run in that project. The moderator table is intentionally not writable by browser roles; a trusted administrator must add moderator UUIDs before moderation actions can be used.

## User flow

Supabase Auth stores and refreshes browser sessions. If Supabase rejects a stored session (including an invalid refresh token), VYBE clears that project's local auth entries and asks the user to log in again; network errors are not treated as expired-session recovery. Login checks the authenticated user's existing profile before routing to the homepage or onboarding. Signup initializes a missing profile without overwriting an existing one and routes authenticated users to onboarding. Email confirmation is enabled in the connected project, so users must confirm their address before a session can be created; the confirmation link returns to onboarding. Email delivery and redirect allow-lists still need to be configured and verified for the deployed origin. Logout explicitly revokes the current device's session, waits for Supabase to finish, and verifies the local session is cleared before leaving protected pages. If the server cannot confirm revocation but local sign-out succeeds, the user is informed rather than shown a success-shaped fallback. Onboarding choices and the current step are upserted as draft progress on each answer and navigation, then marked complete only after the final save succeeds and the user is redirected to the homepage. Returning users reload the saved answers and resume at the saved question.
